# Android call-audio telemetry (CallAudioRelay RELAY_HEALTH, PcmLevelMeter, uplink PCM path, hearing flag, iPhone telemetry storage, DiagnosticsReport)

## Summary
RELAY_HEALTH is built in CallAudioRelay.tick() on the "CallAudioRelay" HandlerThread. It is written every 5 s, and only while mediaRunning, to logcat and to call-diagnostics.log under the tag "Audio". The downlink level meter is the pure-JVM class PcmLevelMeter. The "CallAudio-Downlink" sender thread feeds it the reused PcmFrameAssembler.frame buffer. tick() drains it with takeLevel(), and startMedia() also drains it once to clear the previous call's level. The uplink path runs in two steps. First, receiveLoop (thread "CallAudio-Receive") checks session, address and counter and runs BridgeCrypto.open (AES-GCM, header as AAD), then acceptFrame() → UplinkJitterBuffer.offer(), but only while mediaRunning. Second, writeLoop (thread "CallAudio-Uplink") does poll() → playbackPcm (16 kHz mono PCM16 LE, 640 bytes; the real frame or the PLC/silence buffer plcBuf) → Upsampler3x into `out` (48 kHz stereo) → track.write(out, …, WRITE_BLOCKING) on a USAGE_MEDIA AudioTrack pinned to TYPE_TELEPHONY (INCALL_MUSIC). Concealment and silence go through the same write call; only a counter (insertedSilenceWrites vs uplinkPcmWrites) tells them apart. Nothing on Android measures uplink level today. The UDP header carries a "hearing" flag (byte 9 bit 0). It is only acted on (lastIPhoneHearingAt), never logged on its own. No mute state travels on UDP or WS: a muted iPhone just sends zeroed PCM. Two WS messages, client_log and client_status, go to IphoneDiagnostics (iphone-diagnostics.log, "MM-dd HH:mm:ss.SSS tag: text", rotated at 512 KB to iphone-diagnostics.1.log, 4000-char line cap, 200 lines per frame, no time-based rate limit). client_status is flattened into one key=value line built from a fixed whitelist of 12 keys. Nothing is kept in memory or used for decisions, and unknown keys are silently dropped. The current iOS build sends only 7 of the 12 keys. DiagnosticsReport.build() returns a JSON snapshot of the Redmi's state. The iOS "diagnostics" WS command requests it, and so do MainActivity's status refresh and its clipboard copy. It holds no iPhone-reported status and no level values.

- The downlink meter is the field `private val downlinkLevel = PcmLevelMeter()` on CallAudioRelay. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:289)
- PcmLevelMeter.add() parses LE PCM16 in place, computes per-frame sum of squares and peak, and counts a frame as active when its own RMS is >= -50 dBFS (SPEECH_GATE_DBFS). Speech RMS averages active frames only. Peak is the window maximum. FLOOR_DBFS -99 is reported for silence or no data. add() and takeLevel() are both @Synchronized. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/PcmLevelMeter.kt:30)
- add() allocates nothing: it uses primitive locals and a loop over the caller's buffer. takeLevel() allocates one Level data class per call (once per health line) and resets the window. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/PcmLevelMeter.kt:53)
- The downlink meter is fed in sendLoop on thread "CallAudio-Downlink" (MAX_PRIORITY, THREAD_PRIORITY_URGENT_AUDIO) with downlinkLevel.add(assembler.frame). This happens after a complete 640-byte frame is assembled and before pacing, sealing and sending. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1250)
- PcmFrameAssembler.frame is one preallocated ByteArray that is overwritten on each completed frame, so the meter input is allocation-free. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/PcmFrameAssembler.kt:16)
- takeLevel() is drained on the worker HandlerThread "CallAudioRelay" (THREAD_PRIORITY_AUDIO) in tick(). startMedia also drains it once (downlinkLevel.takeLevel()) so the first line of a call does not report the previous call. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1075)
- PcmLevelMeterTest has 3 JVM tests: speechLevelIgnoresSilentFrames (-20 dBFS, 50% active), quietLineReportsItsRealLevel (-40 dBFS) and takeLevelStartsAFreshWindow (-99/-99/0). Its square() helper builds 640-byte LE frames. (RedmiGateway/android/app/src/test/java/com/ilkay/redmigateway/audio/PcmLevelMeterTest.kt:8)
- Uplink receive: receiveLoop on thread "CallAudio-Receive" checks session id, the allowed client address and counter > lastRxCounter. It picks a reused scratch buffer by ciphertext length, builds the nonce ("UPLK" + counter + session), copies the 10-byte header as AAD, then calls BridgeCrypto.open(key, sealed, header). A null result increments rejectedPackets. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:870)
- BridgeCrypto.open uses a new Cipher instance and doFinal, so it returns a newly allocated plaintext ByteArray per packet. The receive path is therefore not allocation-free, despite the scratch buffers. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/security/BridgeCrypto.kt:54)
- Type 1 (640 B) becomes frame = plain. For type 2 (1280 B) the current frame is plain.copyOfRange(640,1280), and the repeated frame is kept only if RedundantFrames.copyIsNew(counter, lastPcmCounter). Protocol 1 copies payload bytes 8..648 in clear. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:893)
- acceptFrame() updates lastIPhonePcmAt, firstPcmAt, iphoneFrames and pcmSinceArm, and kicks the gate. It calls uplinkQueue.offer(frame, receivedAt, authenticated) only when mediaRunning, so frames received while PREPARING without media are counted but never queued. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:953)
- writeLoop (thread "CallAudio-Uplink", URGENT_AUDIO) does frame = uplinkQueue.poll(now). A valid 640-byte frame becomes playbackPcm = frame, with RAMP_UP applied in place to its first 32 samples after 3 or more PLC frames. Otherwise PLC writes plcBuf (x0.75, x0.40, a fade from 0.20 to 0, then zeros, or zeros with no history) and sets playbackPcm = plcBuf. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1106)
- The 16 kHz mono PCM16 LE samples right before the write are held in `playbackPcm`. upsampler.process(playbackPcm, 0, FRAME_SAMPLES, out) produces 48 kHz stereo in `out`, and the write is track.write(out, 0, bytes, AudioTrack.WRITE_BLOCKING). Real PCM and concealment/silence go through this same call. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1178)
- After a full write, frame == null increments insertedSilenceWrites and otherwise uplinkPcmWrites. A short write increments partialUplinkWrites. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1209)
- The uplink AudioTrack is USAGE_MEDIA/CONTENT_TYPE_SPEECH, 48 kHz stereo, MODE_STREAM, a 6-frame buffer, and setPreferredDevice(TYPE_TELEPHONY) (INCALL_MUSIC output). (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:1332)
- The hearing flag is sealed header byte [9] bit 0 (FLAG_IPHONE_HEARING = 0x01). It is parsed only after a successful GCM open, so it is authenticated as AAD, and it sets lastIPhoneHearingAt. Other bits are ignored. (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:891)
- The hearing flag is used in tick() as the iphoneHearing gate input to CutoverDecision.canHandOver, and for the IPHONE-owner fallback "iphone_not_receiving" after deafLimitMs (2 s local, 5 s remote). (RedmiGateway/android/app/src/main/java/com/ilkay/redmigateway/audio/CallAudioRelay.kt:775)

## Risks
- Feeding the uplink meter from plcBuf as well as real frames would mix concealment into speech/active%. Only add when frame != null, or use a separate counter. insertedSilenceWrites already counts substituted frames.
- The RAMP_UP block modifies the polled frame in place (CallAudioRelay.kt:1111-1121). Measure before it, or the first 32 samples after a gap are slightly attenuated.
- PcmLevelMeter methods are @Synchronized. add() on the URGENT_AUDIO writer thread adds an uncontended lock per 20 ms frame (same as downlink); takeLevel contention happens only once per 5 s. Do not call takeLevel from diagnostics(): it empties the window the health line reads.
- RELAY_HEALTH is parsed by first-match regexes in scripts/analyze-call-diagnostics.ps1 (dropped=, underruns=, maxWriteMs=, silence=…/s; PowerShell -match is case-insensitive). New fields must not contain those substrings, or must be appended after the originals.
- The WS message cap of 16,384 chars (GatewayWebSocketServer.kt:197) applies to the sealed, base64 envelope. A richer client_status or bigger client_log batch over roughly 12 KB of plaintext is dropped silently, with no log.
- IphoneDiagnostics uses an unbounded single-thread executor queue and reopens the file for each line. A higher status cadence or per-frame telemetry could grow the queue and churn the 512 KB rotation, pushing call evidence into the .1 file and then deleting it.
- The client_status whitelist means any new iOS field is lost silently until Android is updated as well. Android and iOS changes must ship together, or the Android side should log unknown keys.
- BridgeCrypto.open and the type-2 copyOfRange allocate a new array for every received packet. The uplink path already allocates per frame, contrary to the 'scratch' comments; any new receive-thread work should not add more allocation.
- An all-zero uplink can mean the iPhone is muted, a dead or denied microphone, or the iOS capture filter blanking a stale generation (CallAudioTiming). The level meter alone cannot tell these apart; an explicit mute signal (flag bit or status field) is needed for certainty.
- The tick() KDoc says 250 ms but MONITOR_INTERVAL_MS is 150 ms. This is a minor doc drift, not a behavior issue.

## Open questions
- Should the uplink meter measure what was actually written to the call (writeLoop, after the jitter buffer: recommended, and analogous to the downlink meter measuring what is sent) or what arrived from the iPhone (acceptFrame, including frames later dropped or expired, and frames from before mediaRunning)?
- Should concealment frames get their own level/ratio field, or is the existing silence=/s counter enough?
- What is the applicationId (package) for the external files path of iphone-diagnostics.log? It was not verified from build.gradle in this pass; the code namespace is com.ilkay.redmigateway.
- Should new iPhone status fields (mute, audio route, engine state, CallKit calls, iOS-side uplink level) go via client_status (60 s cadence plus app state changes) or a new, more frequent in-call message? client_status is too slow to catch mute toggles during a call.
- Should the latest iPhone status be persisted across Redmi process restarts (a file), or only held in memory for DiagnosticsReport?
