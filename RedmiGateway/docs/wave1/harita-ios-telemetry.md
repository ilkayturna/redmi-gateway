# iOS app diagnostics sent to the Redmi (repo root C:\Users\ilkay.turna\source\repos\redmi-gateway)

## Summary
Every iOS log line goes through GatewayConnection.log(), which writes it to three places: a 200-line UI ring, Documents/app-log.txt (written asynchronously, rotated once at 512 KB) and a 300-entry memory-only telemetry ring. While the socket is authenticated, the telemetry ring is pushed as sealed `client_log` frames: up to 40 lines per frame, a 5 s timer, and forced flushes on auth, didBecomeActive and didEnterBackground. A batch counts as delivered as soon as send() is called. The send completion is ignored and the Redmi never acks. Offline lines stay only in memory; the oldest drop at 300 and the drop count goes to the Redmi.

Crash capture covers only NSException. NSSetUncaughtExceptionHandler writes Documents/last-crash.txt. The next launch logs "Previous run crashed: …", deletes the file, then replays the last 40 physical lines of app-log.txt as "Previous run (last N log lines)". There is no signal handler, no MetricKit, no OSLogStore and no os_log.

`client_status` is sent on auth, every 60 s and on foreground/background changes. It carries appVersion, appBuild, appState, mic, battery, thermal and lowPower. The Redmi already has slots for callkit/audio/notify/ble/network, but iOS never fills them. Any other key is silently ignored by the Redmi.

Mute (CallKit CXSetMutedCallAction → AudioEngine.isMuted → CallAudioCaptureMute) is never logged. CAPTURE_HEALTH and DOWNLINK_HEALTH are computed every 5 s on the audio networkQueue and logged through main → GatewayConnection.log. They have no level meter and no mute flag.

Build settings: deployment target iOS 15.0, Swift language mode 5.0, single app target, no XCTest. Tests are standalone swiftc executables run in build-ios.yml.

Critical constraint on the Redmi side: it silently drops any WebSocket text over 16,384 chars and truncates lines over 4,000 chars. Every new diagnostic (crash stacks, MetricKit JSON) must be chunked and byte-budgeted.

## Risks
- Silent loss of large batches (unverified): the Redmi drops any message over 16,384 chars before decrypting (GatewayWebSocketServer.kt:197). iOS marks the batch delivered anyway (GatewayConnection.swift:1667) and ignores the send completion (1394). The first batch after a crash carries the full stack plus up to 39 replayed lines, so it can exceed the limit and disappear with no trace on either side.
- Race at launch: reportPreviousCrash's LogFile.append is async (GatewayConnection.swift:1787), while replayTail reads the file synchronously right after (RedmiGatewayApp.swift:18-23). The crash text may or may not also appear inside the replayed tail. If it does, the stack is sent twice and the batch grows further. Because the crash entry has embedded newlines, its stack lines also consume the 40-line tail.
- replayTail runs on every launch, including iOS background relaunches (BLE restoration, region, VoIP/silent push). Replayed lines are re-logged into app-log.txt, so later launches can replay earlier replays, which adds duplicates and nested timestamps on the Redmi.
- LogFile writes are async on a utility queue, so the last lines before an abrupt termination may never reach app-log.txt.
- sanitizeTelemetry masks any 8+ digit run, including numeric session ids (AudioEngine.swift:251,256) and parts of stack addresses or offsets. Only the Redmi copy is affected; the local app-log.txt keeps them.
- Background catch-up closes the socket immediately after sync (GatewayConnection.swift:1537-1546), so a backlog over 40 lines is not delivered on a background wake.
- Any new client_status key outside Redmi STATUS_KEYS is silently dropped until an Android build ships. iOS and Android release independently.
- Reading self.isMuted while holding captureLock (e.g. inside captureHealthTick's locked block) deadlocks, because NSLock is non-recursive.
- Touching the tap closure, the pacer or the networkQueue timers can change audio timing. Keep meters as plain counters in sendPcm/captureHealthTick and do no allocation or logging per frame.
- MetricKit JSON payloads can be tens of KB. Logging them unchunked breaks the 4,000-char line and 16,384-char frame limits. didReceive runs off the main queue, and heavy work must not run on main during a call.
- A custom POSIX signal handler is risky: it must be async-signal-safe and must not break the system crash reporter. MetricKit MXCrashDiagnostic is the safer route for Swift traps.
- A new .swift file passes the CI typecheck step (which uses find) but fails or is excluded in xcodebuild unless all 4 pbxproj entries are added.
- Adding device details to the plaintext auth frame (GatewayConnection.swift:830) exposes them on the LAN. Use the sealed client_status or client_log instead.
- The CallScreen mute button state is synced only onAppear (CallScreen.swift:21-23), so a mute from the system UI can show inverted in-app. Logging will expose this, but it is a separate UI bug.
